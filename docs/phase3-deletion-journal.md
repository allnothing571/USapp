## 2. v1 离线记录格式

每行一个 JSON 对象，以换行结束；不完整的最后一行、重复 JSON 字段、未知字段或非法枚举都拒绝。所有 UUID 必须使用规范的小写格式。

| 字段 | 内容 |
|---|---|
| version、journal_id | 格式版本 1、部署日志身份 |
| seq、event_id、previous、hash | 从 1 连续递增、唯一事件 ID、前一行摘要、本行摘要 |
| intent_id | 一次操作身份，确认记录引用相同身份 |
| action | delete、undo、purge、cleanup（只允许 media；第 11 节） |
| phase | intent、committed、aborted |
| target_kind、target_id、cycle_id | memory 或 media、目标、确切删除轮次 |

摘要由除 hash 外的所有字段，按键排序、紧凑分隔符的 ASCII JSON 编码计算 SHA-256。首行 previous 为 64 个零。没有标题、正文、文件名、对象键、签名链接或账户标识。不使用时间戳推断先后或截止日期；seq 是恢复协议的逻辑顺序。

检查点只有 version、journal_id、seq、head。校验必须要求日志身份与调用方预期一致、记录数与 head 完全一致；过旧检查点、未知尾部追加或尾部缺失都拒绝。空日志也必须有独立可信的零检查点。

**信任边界：** 哈希链不是签名，不能抵御能同时改写日志和检查点的人，也不能证明所有业务操作曾被写入。检查点必须来自独立可信的最新头记录，并有生产保管、访问控制与完整性保证。如果只是从同一损坏日志重新算一个检查点，校验毫无意义。生产适配器和检查点提供者尚未实现，不能用本工具通过的结果认定备份覆盖完整。

## 3. 恢复语义

1. intent 必须先于实际效果并持久化在 PostgreSQL 之外。committed 只在效果确定提交后追加；aborted 只能表示已经证明没有效果，超时不能写成 aborted。终结记录必须与原操作目标、轮次和动作完全相同，且只允许一次。
2. 每个目标的删除轮次永久唯一；撤销和清除必须引用已经存在的删除 intent。对已证明中止的轮次出现未中止的后续动作，日志拒绝。
3. 未确认的删除按隐藏处理；未知撤销不解除隐藏。已确认撤销只解除同一轮的隐藏，另一轮删除不受影响。删除确认晚于撤销确认到达时，不按确认到达顺序再次隐藏旧轮；逻辑先后来自 intent 顺序。
4. 未确认或已确认的清除均形成不可开放屏障；即使日志同时出现确认撤销，也不推断字节或文字已经恢复。已证明中止的清除不产生该屏障。
5. 回忆及其历史照片级联必须分别覆盖每个目标。测试只验证记录齐全时如何组合；**没有实现数据库读取级联清单和逐项持久化，不能发现日志中从来没有记过的照片**。
6. 计划输出只有 cycles、hidden_targets、purge_barriers、unresolved_intents 和已校验头信息；没有白名单。没有出现在隐藏集合中的目标，不等于允许读取。所有计划固定 `serving_allowed: false`、`status: replay_required`。

## 4. 本地执行

只对合成数据或已获授权的离线副本运行；真实日志虽无正文，仍包含隐私相关 ID，不入库。

```powershell
python -B tools/deletion_journal.py --journal <snapshot.jsonl> --checkpoint <trusted-head.json> --expected-journal-id <uuid> --output <new-plan.json>
```

成功退出 0，只表示指定快照通过格式、链和状态校验并生成了待重放计划，固定输出 `JOURNAL_VALIDATED_REPLAY_STILL_REQUIRED`。失败退出 2，仅输出 `JOURNAL_PLAN_BLOCKED`，不回显输入内容或路径。输出文件必须不存在，禁止覆盖旧计划。计划是离线报告，不是恢复授权凭据；未做持久化或防伪保证。

测试命令：

```powershell
python -B -m unittest discover -s tests -p test_deletion_journal.py -v
```

## 7. J2a 异步提交协议（2026-11-06）

### 7.1 已实现

`services/api/src/services/DeletionJournal.h` 是只依赖 C++17 标准库的异步协议核心。`Journal` 提供整批意图确认和整批最终确认；`Effect` 提供使用稳定身份的执行或分类；`Coordinator` 保证调用顺序。它还没有生产调用方，没有配置开关，也不绕过现有服务的身份验证或幂等分类。

准备好的 Operation 包含一个稳定 UUID、一种动作（delete/undo/purge）及所有 Subject（memory/media、目标 UUID、确切轮次 UUID、意图 UUID）。清单排序后不可变；同一目标一批不能出现两轮，意图 ID 不能重复；格式错误在任何外部调用前拒绝。同一 Operation 重试必须复用所有 ID，不能根据每次重读重建一份不同的清单。

执行状态：

1. 日志确认整批意图已经持久化后，才调用效果接口。不可用、异常、确认丢失或清单冲突均不执行效果。
2. 效果返回已提交才写 committed；只有证明未执行才写 aborted；异常或未知提交不写任何最终确认。
3. 效果已提交但最终确认未成功时仍返回 Unknown。重试先查日志已知终态；若仍待确认，再由效果接口在稳定键下分类。不能盲目重做，也不能靠协调器自身内存判定恰好一次。
4. 同一执行器上重复回调只接收一次。每个请求的回调必须串行，**不提供任意多线程并发回调安全**。适配器还必须自行提供有界超时；核心没有定时器，永久不回调会让请求悬置。
5. 底层日志须保证整批原子持久化及操作 ID 的内容绑定，含目标清单；最终确认不能翻转。当前假适配器只是在内存中模拟此保证。J1 v1 行格式自身没有批次完整性字段，不能证明生产存储真的做到了整批原子性；J4 须证明此保证或升级日志格式，不能用本批结果略过它。

### 7.2 真实入口接入前必须满足的边界

实际读取发现：`MediaService::deleteStart` 在持有 33018 后生成删除行 ID；`MemoryService::writeCycle` 在 33020 下取得照片锁并运行级联；`MemoryPurgeJob::runLocked` 在调度事务内调用擦除函数。外部日志不能简单插入这些位置。

- **先授权、再准备。** 不允许未授权的目标 ID 进入可影响恢复的日志。准备阶段必须分类已有幂等键、读取确切轮次和候选级联清单，期间不得保留数据库事务或锁等待外部存储。
- **记录后重新核对。** 效果适配器开始自己的事务，按现有顺序锁定、分类、验证角色和期限，核对目标清单仍完全相同，才提交效果。新增加或消失的照片不能静默更新原批次；应证明本次没写，结束这批，再用新的准备流程处理。
- **完整证明。** 事务回滚请求不等于服务器已回滚，`RESULT_UNKNOWN` 也不是未执行证明。若不能确认本次及同键其他在途尝试都不能再提交，不能写 aborted。
- **审批与拒绝分开。** 同意删除须覆盖决定、回忆周期与所有关联照片；单纯申请、拒绝和撤回不执行删除。稳定操作身份必须跨进程、重启与重试保存，不能只放在前端或 C++ 内存中。
- **清除单独拆分。** 媒体 `removeKeys` 在任务事务外执行删除，可在取到完整计划后加入意图；文字清除需要先枚举、释放准备事务、记录意图，再事务内核对和擦除。当前实现均未改变。

效果接口的这些责任目前由假效果模拟，**没有完成真实 SQL 或业务服务适配器**。接口不是权限证明、事务证明或发布屏障。

## 8. J2b1 媒体服务接入（2026-11-06）

### 8.1 实施范围

`MediaService::deletePhoto` 和 `undoDeletion` 新增可选 Journal 路径，调用 `configureDeletionJournal` 注入后才使用。每个请求快照保存提供者。`main.cc` 和控制器没有配置提供者，没有新环境变量或默认启用；空提供者仍走既有路径。本批只接媒体删除与确切轮次撤销，回忆、审批、级联、清除和恢复屏障不在此批。

准备阶段只用连接池读语句，不创建事务或取得 advisory 锁：先检查成员和自己的旧幂等键，指纹不符立即拒绝；旧键读取原轮次事实。新键再核对目标属于当前空间且由调用者上传，或待撤销轮次由调用者删除。未授权的目标不进入日志。实际效果仍使用原服务的成员锁、33025 键锁、分类和 33018 目标锁及所有状态/期限守卫。

新增的操作、意图和新删除轮次 ID 来自隔离的 `usapp.media-journal.v1` 命名空间，对调用者、动作、原键的 JSON 数组计算 SHA-256，再派生 128 位 UUID。它们跨同键请求稳定；目标与轮次由日志提供者绑定为不可变清单，换目标会冲突。原键和调用者不写入日志。旧路径依然由数据库生成轮次 ID，新路径才传入准备好的 ID；迁移、权限和契约不变。

### 8.2 最终确认和未知结果

- 意图持久化未确认时，不开始删除或撤销事务，返回现有 `RESULT_UNKNOWN`，保留原键重试。
- 实际效果成功后，用独立读事务重新取得同键 33025 围栏，检查数据库同键记录的指纹、确切轮次，**等待该读事务提交确认**后才调用日志最终确认。这样旧重放的“已请求回滚”不会被误认为锁已释放。
- 日志最终确认失败或回执丢失，效果虽然可能已经提交，仍返回 `RESULT_UNKNOWN`。重试从数据库原键和日志原操作恢复，不换轮次、不重复删除，也不改变截止时间。
- 业务拒绝继续返回原拒绝；外部意图保持待确认，**不把回滚请求或当前查无记录写成 aborted**。这可能保守隐藏一个实际未执行的准备轮次，后续核对机制须处理，不能宣称已解决全部不确定性。
- 日志已有 committed、但恢复后的数据库没有匹配事实时，不再次执行效果，也不返回伪造成功；保持未知，等待恢复屏障。普通内容读取尚未被恢复屏障接管，故这个局部行为不构成可上线恢复保证。

## 10. J2c1 文字擦除接入（2026-11-06）

### 10.1 调度与实际效果分开

`MemoryPurgeJob` 新增可注入 Journal、后台 busy 状态和内存报告。没有真实提供者配置，没有环境变量、迁移、权限、契约或部署修改；`MEMORY_PURGE_ENABLED` 默认仍关闭。空日志路径保留原来的调度事务批量擦除；有日志时，在调度事务内只从同一 `usapp_memory_purge_due()` 选最多 50 条到期且非共用文字候选，提交后才启动日志工作。

afterCommit 只捕获候选 ID、提供者和共享后台状态，不捕获旧 Transaction 或 TxScope。意图确认后，每个效果另开异步事务，取得 33020，核对确切轮次属于准备的回忆，再调用原 `usapp_memory_erase`。原角色安全校验、到期、未撤销、共用文字及擦除守卫没有改动。真正事务提交确认后才允许日志最终确认；业务或数据库错误保持 Unknown，不推断 aborted。

**与旧批量路径的区别：** 有日志的路径逐轮提交，一轮失败不回滚其他回忆；调度 completed 只表示候选选择和排队提交成功，详情写 queued，不声称全部擦除成功。真实擦除仍看不可变 `memory_purges`。`journalReport()` 的 confirmed/unknown/cancelled 是这轮操作与核对计数，不是新增擦除行数，也不是持久审计日志。

每条清除 Operation 用删除轮次派生稳定 ID，动作 purge，只包含回忆与确切轮次；指纹不含文字或旧正文指纹。协调器认为已确认，但当前数据库没有对应 `memory_purges` 行时，报告 Unknown，不凭外部终态重做效果或宣称恢复已完成。

### 10.2 擦除后缺失确认的补偿

擦除已提交后，原到期函数不再返回该轮次。所以只重试到期清单，会永久漏掉日志确认失败。新路径另从 `memory_purges` 每轮读最多 50 条历史记录，按删除轮次 UUID 做循环 keyset 扫描，到尾部时回绕；每轮最多两次读取以处理回绕。去掉当轮到期候选的重复项，再按同一操作 ID 重试。

历史项不会新增擦除：已确认日志直接核对数据库；尚缺确认时，原函数返回 already 后提交并补充确认。真实新擦除仍受 50 条到期候选限制，最多另有 50 条历史确认核对。游标只在内存，不是永久水位；进程重启从头核对，晚提交在以后回绕时发现。历史数量、写入速率和核对时延没有生产测量，不承诺固定修复时限。

同一 job 对象在后台工作时拒绝启动第二轮，记录 busy；跨进程不依赖此 busy 标志保证恰好一次，而依赖稳定日志身份、原擦除函数、33020 和不可变清除行。生产日志仍须满足跨进程原子持久化与回调时限要求，本批没有证明那些性质。

开关关闭时不选择、不调用日志。等待意图时关闭开关，会在效果入口再次检查并保持未知，不执行擦除；效果事务内也有开关检查。不能把这一点扩大成可取消已经提交或提交结果未知的操作。

## 11. J2c2 对象清理接入（2026-11-06）

### 11.1 删除路径清单

`MediaService` 中调用 `ObjectStore::remove` 的位置只有三处，本批全部接入：

| 路径 | 原入口 | 含义 |
|---|---|---|
| 计划清扫：首扫与复扫 | `removeKeys`（`runTick` 的 afterCommit） | 一个清理计划（媒体 + 范围）的一次扫描，原因可为 user_deleted、rejected、abandoned、unattached 或 leftovers 的 ready |
| 迟到对象 | 对账器 `classifyKeys` | 数据库判为 late 的键 |
| 恢复的上传尝试 | `abandonAttempt` | 恢复执行的尝试删除自己写的键（late 或 pending_sweep） |

没有其他服务调用删除：`AlbumService`、`MemoryService` 等不直接删对象。未配置日志时三条路径完全保持原样。

### 11.2 协议扩展：cleanup 动作

J2a 只有 delete、undo、purge，而 purge 必须引用已存在的删除轮次。rejected、abandoned、unattached 和 leftovers 的清理**没有用户删除轮次**，不能编造一个，也不能不记日志。因此新增窄范围动作 `Cleanup`：

- 只允许媒体目标（`normalize` 拒绝 memory），轮次 ID 由清理计划（媒体 + 范围）派生，**不是**用户删除，也不需要事先 delete。
- user_deleted 计划仍用 `Purge`，轮次是计划上的 `deletion_id`。计划缺少 `deletion_id` 时不执行，也不补造轮次。
- J1 离线校验器接受 `cleanup`：只能是 media；同一计划可有多次意图；未证明中止的 cleanup 进入 `purge_barriers`，不进入隐藏集合。新增 3 项测试，共 28 项。
- 假日志按同样规则处理；`exportEvents` 输出 `cleanup`。

### 11.3 身份、重试与状态

- **身份。** 每个操作 = (计划、范围、扫描种类 first/sweep) 或 (迟到键、来源 reconcile/attempt_resume)，再加 epoch。操作 ID、意图 ID 由独立命名空间稳定派生。日志中只有媒体与轮次 UUID；对象键只以摘要形式进入 `requestFingerprint`。
- **载荷绑定。** 指纹覆盖原因、确切删除轮次、来源和按序排列的全部键。同一身份下目标或载荷变化，日志返回冲突，而不是执行。
- **重试。** 丢失回执、部分失败、存储无响应都重用同一 epoch，再次执行仍是同一操作。
- **必要的后续删除不被抑制。** 某 epoch 已有终态（本轮未执行），而数据库仍要求这次删除（扫描仍被选中、键仍为 late），就进入下一 epoch，作为新操作执行。初版将 16 误作整个操作历史的上限；11.9 的待验证修复将其改为每轮窗口，下一轮接着检查。
- **不全局削弱删除/撤销去重。** epoch 只用于清理；J2b1/J2b2 的删除、撤销身份和协调器的终态短路都没变。
- **从不写 aborted。** 拒绝时无法证明同一操作的早先尝试一个键也没删，所以只留下未决意图（恢复计划按屏障处理），不写已中止。

### 11.4 效果的复核与顺序

所有日志和存储调用都在单条连接池语句之间进行，不持有事务或 advisory 锁。

1. 准备：读取计划事实（原因、轮次、扫描是否已记录、复扫是否到期、按规则计算的键），或键的事实（所属媒体、状态、计划）。
2. 日志确认意图持久化后才进入效果。不可用、回执丢失或冲突都不调用存储。
3. 效果内重新读取权威事实：同一计划、同一轮次、同一组键（指纹一致），复扫已到期，且**每个键**当前状态都是 `pending_sweep` 或 `late`。任何 `keep`、`live`、`unknown` 或事实变化都拒绝，一个键也不删。迟到键要求状态为 `late`（恢复尝试也允许 `pending_sweep`）。
4. 逐个删除；只有全部键已删除或确认不存在，才写扫描记录（`media_cleanup_passes`）。之后返回 Committed，再由协调器写最终确认。
5. 扫描记录写入失败或任一键失败：效果 Unknown，不写扫描记录，下次同一操作重试。
6. 迟到键删除成功但删除记录写入失败：键已确认消失，仍返回 Committed，只是缺少审计行。

### 11.5 缺失最终确认的补偿

扫描一旦记录，正常选择就不再返回它，所以只靠重试会永久漏掉确认失败。每轮另按游标循环读取最多 50 条已记录扫描和 50 条 `removed` 迟到记录，按日志中冻结的载荷逐个 epoch 查找：

- 扫描：数据库已记录且当前指纹一致时补充确认。
- 迟到键：存储确认键已不存在时补充确认。

这一过程从不删除对象；游标只在内存中，进程重启后从头开始。

### 11.6 本批发现并修复的实现问题

- **队首阻塞。** 有日志时，没有登记删除意图的旧 user_deleted 计划每个 epoch 都冲突，永远无法完成。原来按创建顺序选取最多 100 条，这些旧计划会一直占满窗口，饿死后来的计划。现在有日志时，用内存游标轮转选取同一规则的工作，无日志路径不变。触及 epoch 上限的操作在本进程内 300 秒内不再尝试（只在内存中，重启后再试）。
- **自锁死。** 第一版退避检查在持有非递归互斥量时调用 `next()`。若被退避的是本轮最后一项，后续同步进入确认补偿，再次加锁，导致整轮清理卡死。已改为释放锁后再继续；其余用到该锁的地方都在调用回调前释放。

两项都是本批新代码的问题，由下列运行发现。

### 11.9 Codex 审查修复：跨窗口推进与跨来源确认（2026-11-06，验证见 11.10）

审查发现两个独立问题：所有后续轮次都重新检查 epoch 0–15，退避结束后也无法越过已完成的窗口；`media_late_objects` 的主键为 `(object_key, disposition)`，而记录写入采用 `ON CONFLICT DO NOTHING`，因此只保留第一次删除的来源，后一次来自另一来源的丢失确认无法被原补偿路径发现。

修复内容：

- 工作与确认各有独立的、按日志提供者所有权隔离的内存 epoch 游标。一次调用最多检查 16 个 epoch，耗尽预算后下一轮继续。游标丢失或提供者重新打开后，从 0 开始分轮查找，不将 16 当作整个历史的上限。epoch 使用 64 位无符号整数，溢出时不回绕复用操作身份。
- 工作遇到已完成操作时推进；遇到冲突先查日志，只有该身份确实存在才可推进。查找未知保持当前 epoch；身份缺失的拒绝在当前 epoch 退避 300 秒。未登记旧删除仍不能清除，不会因此创建新轮次绕过登记要求。原未决意图不被中止或删除。
- 确认游标遇到权威 Missing 时回到 0，后续轮次重新检查更早的未决确认；Unknown 不推进。确认过程仍只读取扫描记录或 HEAD，不调用删除。
- 每条 removed 迟到记录同时检查 `attempt_resume` 和 `reconcile` 两个操作命名空间，不再把第一条记录的来源当成完整历史。

新增两项数据库回归用例（含两种来源顺序）：

1. 在真实首个 late 删除的操作模板上，为假日志准备 epoch 0–16 的已完成历史。第一轮不得越过 16 个检查预算或删除对象，后续轮次必须删除；epoch 17 的最终确认失败后，重新打开同一假日志、丢弃本地游标，必须只补确认且不再次删除；之后再次落地仍可在 epoch 18 删除。重新打开只模拟游标丢失，不是真实进程或持久提供者恢复。
2. 真正的恢复上传路径和协调器按两种顺序删除同一键。数据库记录保留第一次来源，第二次删除的最终确认失败；恢复确认能力后必须补齐且不增加删除请求。

## 12. J3a：始终关闭的恢复准备协议（2026-11-06）

### 12.1 范围与实现

### 12.2 准备流程

1. 请求携带预期日志 UUID、恢复数据库实例 UUID 和尝试 UUID。恢复实例必须由恢复操作之外的可信来源固定，不能只是 `usapp_test` 这样的库名，也不能仅相信旧备份自带的标记。
2. `Store.close` 必须先提交 CLOSED 标记和递增的代次围栏。只有确认持久提交且返回实例、尝试和非零代次全部一致，才能查询外部日志。未收到确认即停止；不得提前暴露监听器或启动后台工作。
3. `Source.snapshot` 的生产实现必须重做 J1 的完整链和状态校验，并固定来自独立可信来源的最新检查点；不能把任意生成计划的 JSON 反序列化后标记为可信。本批只测试假来源，没有实现生产校验适配器。
4. 协调器检查快照头、日志身份、目标类型、规范 UUID 和重复项，并排序清单。零检查点必须同时具有零摘要、空隐藏清单、空清除屏障及空未决清单；非零检查点不能使用零摘要。隐藏目标、清除屏障与未决意图全部交给 `Store.stage`，不得用“没有出现在清单里”推断可开放。
5. `Store.stage` 必须在同一围栏下原子持久化整个清单，不能静默遗漏目标或清除既有隔离。`Store.verify` 随后读回实际持久效果；真实实现必须核对包括历史、提案、计划父链接、媒体读取及旧幂等响应在内的所有路径，不能只看写入行数。
6. 核对之后重新取得独立最新检查点。序号向前、向后、相同序号但不同摘要或日志身份变化都不能记录准备成功；日志不可用仍保持关闭。

### 12.3 异常、重试与并发

- 缺少任一适配器、非法请求身份直接拒绝；来源不可用、验证失败、异常或未知提交均不能获得开放结果。错误结果不包含原始输入、目标正文或凭据。

### 13.1 持久状态与权限

新增 `0042_deletion_recovery.sql`，只在一次性临时库应用。首次提交运行 `usapp-j3b-c7f0aaf708`，SHA-256 **`fa72f1308ed32098319ca613e7af099f799f00d57739429ac1d99919746743a0`**，自该次提交起冻结；0000–0041 未修改，下一迁移号 0043。

- 唯一新增的 SECURITY DEFINER 是 `usapp_recovery_closed()`：无参数、固定布尔查询、固定 `pg_catalog, pg_temp` 搜索路径、不写数据。它让原擦除角色看到关闭状态，而不增加该角色的表权限。

### 13.2 围栏与核对

维护操作在事务内持有独占 33026 锁，按代次核对恢复实例、尝试和最新 generation；不取得域锁。新关闭操作使旧代次失效。stage 原子保存完整清单和全部隔离项目；同一代次同一清单可重试，改变内容即冲突。旧清单和旧隔离均不删除。

`verify` 不只看行数：核对整份 JSON、隔离项目的双向集合差、读屏障函数，以及 32 张域表实际启用的行级安全、写触发器与严格策略表达式/角色。关闭检查点的同序号不同摘要、序号或日志身份变化仍由 J3a 拦住；record 重新核对代次、清单、精确头和屏障，且始终保持关闭。

适配器使用显式事务；只有提交回调确认成功才返回 Confirmed。错误、未知提交或权限不足返回 Unknown，不把 SQL 已返回一行当成提交成功。为此增加 `TxScope::beginOnClientAsync`，原普通 beginAsync 仍调用原应用池，保持其异常处理。

### 13.3 实际读取与写入隔离

关闭操作提交之后，不只隔离清单中的单个目标，而是保守关闭整个媒体/回忆相关域；**没有任何自动解封能力**。即使核对记录存在、快照是空的或所有步骤成功，也不开放服务。

- 原有媒体/回忆的 deleted-now 函数增加关闭条件，供当前读取、父链接、照片占位和状态判断使用。
- 对 32 张媒体、回忆、相册及计划-回忆链接表启用行级安全。permissive 基础策略不增加表权限，restrictive 策略在关闭时使应用与擦除角色读不到这些行，不能被额外 permissive 策略覆盖。原始表查询、历史正文和旧幂等收据的查询也受约束，不仅依赖当前服务代码。
- 应用角色必须不是超级用户、不能 BYPASSRLS、不能拥有这些域表或通过角色成员资格绕过约束；迁移、恢复核对和启动权限检查覆盖相应条件。可信维护所有者仍可读原数据，这是维护边界，不是物理擦除。
- 域写入的语句触发器取得共享 33026，关闭操作会等待已开始的域写事务结束；随后新的写入被拒绝。调用者必须使用 READ COMMITTED，其他隔离级别显式拒绝，避免旧快照绕过等待后的关闭检查。这是对数据库调用方式的新约束；正常 API 默认使用该级别。
- 本批不改原计划正文（O12），不改原删除/撤销的期限或来源规则，不读取或删除真实对象。

这不是在线紧急撤销：已经在途的读取、发出的签名链接、客户端已取得的字节，以及外部存储中已经在途的操作不能由此收回。恢复仍必须在停掉旧 API/后台实例的维护环境执行。J3c 尚须在监听及调度前落实启动约束，并解决备份自带标记不能证明最新状态的问题。
