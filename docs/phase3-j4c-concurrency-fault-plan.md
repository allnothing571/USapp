# J4c11：共享前驱竞争与提交答复丢弃测试准备

后续（2026-11-07）：[C11a 受限入口](phase3-j4c-reply-loss-trial.md)已实现、默认 dry-run，本轮 261 项离线测试分组通过；原 5 秒/20 秒限制保留。没有真实云调用。下文为原准备方案，C11b 仍仅设计，实际 C11a 日志扩展需另行批准。

状态（2026-11-07）：**方案及测试内原型完成，尚无本批实时运行器或云端运行命令。** 用户同意准备这批受控测试。本批没有读取真实密钥、访问实际桶/表、并发提交、注入真实网络故障、初始化、清理、部署或启用业务服务。J3 继续暂缓。

## 1. 起点与最小范围

以用户已完成的 J4c9 正向结果及 J4c10 v3 三项权限负例为起点，保留四个既有本地证据目录。实际资源仍为上海、usapp-j4c-log-e3784866 / uj4ce3784866 / journal，journal_id 0afe377a-3e06-4134-997f-4f1a437b8492，原审阅包摘要不改。

已知起始状态：两条批次，旧合成操作为 intent → aborted；一条 permission_probe/write-guard-v1 保护行。云端必须重新核对完整链、索引、bootstrap、保护行和旧两对象；不能凭本地 completed=true 或“表非空”通过。未知/额外历史停止，不清表、不补初始化、不换日志、不扩大权限。

新操作的 operation/target/cycle/intent 从本轮 journal UUID 和固定场景标签派生，只表示不存在的合成媒体。不能从命令行输入业务 ID、任意 payload、purge/cleanup、云操作列表或网络目标。

先做 C11a，再单独准备 C11b；每批先完成受控入口和离线验证，再确认具体云端运行范围。不并行跑多个方案，不为此创建新桶、实例、表、策略或密钥。

## 2. 三种“丢答复”必须分开

| 场景 | 能观察什么 | 不能宣称什么 |
|---|---|---|
| SDK 已解析成功提交答复后，客户端包装层主动丢弃 | 本地确实观察过成功答复，但发布调用者收到未知；可检验回读/重放逻辑 | 不是真实网络丢包，也不证明供应商持久性/故障切换 |
| 桩服务已应用提交后关闭连接 | 自建服务模型中的应用后断连 | 不证明真实 TableStore 的传输/提交行为 |
| 真实请求超时/工作进程被杀 | 调用者未确认；远端可能已应用 | 不能按超时认定未应用，也不能自动标记 aborted |

**C11a 默认只做第一种。** 不关闭真实网卡、不使用代理截断真实 TLS（Transport Layer Security，传输层安全）连接、不杀不属于本次的进程、不变更账号或网络配置。真实丢包/进程强杀另列方案，不混成同一个“故障恢复已通过”。

## 3. C11a：一次成功提交答复丢弃（最先实施）

1. 固定新操作 L，检查其尚不存在，实际链恰为起始两批次；预先保存所有派生 ID 与前驱事实。
2. 正常发布 L 的 intent；只有 SDK 已验证并解析成功的 CommitTransaction 返回之后，测试包装层记录固定的 sdk_success_observed 标志，再向发布调用者抛出固定异常。旧 Metadata 逻辑必须返回 UNKNOWN，不在提交后自动 AbortTransaction。
3. 标志和阶段证据写入父进程控制的本地账本，不保存密钥、原始答复或事务 ID。标志写入失败、没触发、进程超时或未回收即停止，不把它算成一次有效的故障注入。
4. 一个新工作进程只读取，独立核对链、索引和 L 的 intent。另以禁止 PutRow/UpdateRow/CommitTransaction/对象 PUT 的传输验证相同 ID/载荷重放能返回原事实；不能先盲目重发“看看是否幂等”。阶段级 API（Application Programming Interface，应用程序编程接口）计数必须证明恢复阶段没有写操作，不能只看对象 PUT 数。
5. 原事实确认后，用独立显式步骤正常发布 L 的 aborted，再用恢复用户回读。正常最终为四条批次，新增两个已引用批次对象。没有实际业务删除或恢复效果。

软件原型另外覆盖 terminal aborted 提交答复丢弃；不默认把它加入首轮云端写入，以免一批过大。恢复只证明精确测试操作的事实，不代表可信当前检查点、防回退或全局恢复完成。

## 4. C11b：两个发布者争用同一个前驱

先确保 C11a 已完整结束，得到明确的四批次基线。若 C11a 未确认，不启动这一批。

### 4.1 分阶段准备，共享前驱而非碰运气

读取并验证同一前驱 H，预先生成 A/B 两条固定合成 intent 的不同候选对象和候选 head。分别完成对象写入及完整回读，再让两个工作进程用同一个 H 参与提交；不以“两个 publish 接近同时启动”代替共享前驱证据。

父进程的同步屏障在任何远端事务、锁或 SDK 调用之前；两个进程必须各自使用独立事务。不能为了等待屏障持有分区事务，也不能让两个线程共用一个 transaction_id。只允许两个自有子进程；屏障等待计入各自截止，等待失败停止。

保留原 Metadata.commit 的独立对象/完整链验证及原子事务写入，不为了跑完截止直接调用裸 UpdateRow 或删除校验。正常预期一份 CONFIRMED、一份 HEAD_CHANGED。记录实际返回与后续读，不能把 UNAVAILABLE/UNKNOWN 当成“竞争失败且未应用”；两个 CONFIRMED、索引与 head 不一致或双分叉都是失败。

### 4.2 竞争后的有限后续

只有所有子进程已回收、结果明确且回读吻合，才可按计划对明确 HEAD_CHANGED 的操作做至多一次新候选发布；复用原 operation/subject/fingerprint，不能换 key 把它当新操作。UNKNOWN、超时或缺失证据不进入这一步，先只读调查。

再分别正常发布 A/B 的 aborted，最终回读三条新增合成操作的事实。没有自动循环、随机压力测试或清理失败候选。

在正常的一次共享前驱竞争中，旧前驱的失败候选会保留为未引用对象；必须记录精确键，不能按“引用列表没有它”就忘记，也不能让发布者获得删除权限。

### 4.3 预期数量，不作实际成功声明

| 起点/批次 | 已引用批次数 | 正常新候选对象数 |
|---|---:|---:|
| 当前已完成状态 | 2 | 已有 2 |
| C11a 完成 | 4 | 新增 2 |
| C11b 两个 intent、一次明确败者新候选、两个 aborted 完成 | 8 | 新增 5，其中 1 个未引用 |

两批合计正常新增最多 7 个对象，云端共 9 个对象，其中 8 个被引用；这是固定理想路径的审阅上界，不是观测结果或所有故障路径的绝对上限。运行器仍须在每次 PUT 前持久记录候选键并预扣额度。预算不足或路径偏离就停止，不能扩大上限掩盖问题。

## 5. 截止、配额与失败收尾

保持每次自有工作进程 5 秒、离线测试进程 20 秒，不因链变长放宽。先用离线服务验证成本；真实验证若超时，保留未知结果并停止。若以后确需把独立对象验证分成多个步骤，必须另审步骤间不可变性/新鲜度依据，不能默默删掉 Metadata.commit 中的独立验证或把缓存当成当前值。

不自动重试 SDK/HTTP（Hypertext Transfer Protocol，超文本传输协议）、不重定向，不把提交后异常解释为失败未应用。保留 parent-owned Trial 的请求、上传、接收和两小时单调窗口限制；并发工作进程共用同一父进程 SQLite 账本，不能每进程各拿一份预算。Windows spawn 的传输要限于已授权密钥的内存，不进入 argv/环境变量/证据。

新增只含固定 API 类别的计数，以区分 POST PutRow/UpdateRow/CommitTransaction 与对象 PUT；原 puts 指标只数对象上传。分别保留：提交发送前、SDK 成功观察、调用者未知、独立恢复读。任何标志缺失均不伪造成确定失败。

已知 J4c9 的 88 请求与 J4c10 累计 91 请求可结转为已知消耗，但不是账号全部请求（早期身份/桶预检等不在这两份账本中）。5 元继续是人工预算，不是自动扣费上限。实际账单、其他程序、存储闲置费用仍需人工查看；不购买资源包或预留容量。

任何失败均保留原目录、候选键和账本，不重置预算、不重新初始化、不自动标记合成意图中止、不自动删除对象或表行。只读租约可能尚在远端，进程被回收不证明租约消失。

## 6. 开始扩展日志前必须明确的影响

一旦从两批次推进为四/八批次，J4c9/J4c10 旧入口中“恰好两批次”的校验将按设计拒绝。旧成功证据继续成立，但**不得拿旧脚本重跑来验新状态，更不得清表以便旧脚本通过**。新运行器必须绑定精确场景允许的操作集合、phase、完整前缀及前驱；保护行保持原样。

旧审阅包保持不变。新本地方案/执行证据需另有场景版本/摘要，不能靠修改 manifest.mode 或本地授权字段伪装用户授权。云端执行前，应展示确切操作和保留影响，再确认该批写入；当前仅准备方案和离线原型。

## 7. 本批最小离线证据

新增 tests/test_j4c_fault_protocol.py，测试内 _PostSdkReplyLoss 原型，无真实运行入口。使用固定真实 SDK 与内存服务，测试中禁止所有 socket/DNS（Domain Name System，域名系统）连接，合成凭据，不读真实文件：

1. intent 成功答复已由 SDK 解析后丢弃，调用者 UNKNOWN；新客户端读取重放 READY，不新增对象 PUT 或 PutRow/UpdateRow/CommitTransaction。
2. terminal aborted 的同类答复丢弃，新客户端返回原 ABORTED 事实，无新增写入。
3. 提交前故障不能被标记为“提交成功后丢答复”；元数据未应用但孤立对象保留。
4. 相同前驱的候选 A 先提交，B 得到 HEAD_CHANGED，候选 B 保留。
5. 反向顺序控制：B 先提交，A 得到 HEAD_CHANGED。

后两项是**顺序软件控制，不是并发执行或真实供应商隔离验证**。本轮没有并发云端测试、回环故障测试、真实故障注入或恢复演练。

基础回归 j4c-sdk-offline-b6fece1d1e.log：244 项通过、无跳过，14.394 秒；补充“不允许回读重放写入表”的断言后，5 项协议测试单独重跑通过，1.563 秒。不能把它们相加成 249 个不同用例；本轮不同用例仍 244。其他独立工作进程组未重跑。没有变更服务端实现、迁移、契约、部署、依赖、角色/策略或原运行器。

## 8. 官方依据与未证明边界

[TableStore 局部事务](https://help.aliyun.com/zh/tablestore/table-store-service/developer-reference/go-local-transactions)规定单分区、读已提交、事务期间写锁及同一事务 ID 不可并发使用；因此屏障必须在事务外，测试使用独立事务。这些是文档约束，不是本轮实测结论。

[OSS PutObject](https://help.aliyun.com/en/oss/developer-reference/putobject)默认同名写入会覆盖；继续要求从未启用版本、禁止覆盖头及完整字节校验。没有保留锁仍不能据此宣称具备完整云端不可变性。官方页面查阅日期 2026-11-07。

真实提交持久性、并发所有交错、SDK 内部/网络层重发、权限完整面、迟到对象、强杀后状态、可信当前检查点、反回退、外部删除日志、恢复/J3/J5 和完整上线门槛仍开放。v2 原始保护行错误原因也仍未知，不用这批结果替它“结案”。
