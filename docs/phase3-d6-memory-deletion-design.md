# D6 整条回忆删除与文本擦除设计

状态：O1-O12 已由所有者批准（2026-11-05）。M1a、M1b、M1c 和 M1d 已实现，并在一次性隔离实例上用假对象存储验证，证据见第 10 到 15 节。M2 前端已实现并通过模拟接口的自动化验证，证据见第 16 节，尚未做真实接口和浏览器验收。**字节清除和文字擦除都不可逆，都只在一次性实例上运行过。`MEMORY_PURGE_ENABLED` 默认关闭，第 9 节的门槛未满足前不得在生产开启。未部署。** 设计依据：`docs/phase3-plan.md` 第 4.8 节、`docs/phase3-d6-media-deletion-design.md`，以及当前的 `0030`、`0033`、`0034`、`0035`、`MemoryService`、`MediaService`、`SharedPlanController`。

## 1. 规则来源

**已批准，不在本次讨论范围内：**

| 规则 | 来源 |
|---|---|
| 回忆由创建者删除，伴侣通过申请流程请求删除，由创建者决定 | 4.8，§29 |
| 照片属于上传者，上传者随时可删，包括在伴侣回忆里的照片 | D6a |
| 提交时停止所有读取和新签名链接，路由返回与不存在相同的 404 | 4.8 |
| 已签发链接和已下载副本无法召回 | 4.8 |
| 7 天恢复窗口，只有删除者可撤销，到期计划提交后不可逆 | D6b |
| 清除后擦除标题和描述；审计只存 ID，不存文字 | 4.8 |
| 回忆、相册和计划的删除是静默的，不通知 | `phase3-plan.md` 第 2 节需求表 |
| 外部删除日志、30 天备份保留和恢复演练是生产门槛 | D6c，4.8 |

**本文提议的默认值，都等待决定：** 第 2 节的生命周期细节和确认文案、第 3 节的照片处理、第 5 节的擦除机制和计划文字规则、第 6 节的批次。决定表在第 8 节。

## 2. 生命周期

### 2.1 状态

| 状态 | 判定 | 谁能看到回忆 |
|---|---|---|
| 正常 | 没有未撤销的轮次 | 两名成员 |
| 待申请 | 正常，且有一条未决定的删除申请 | 两名成员 |
| 已删除 | 有未撤销的轮次，未清除 | 只有创建者的恢复列表能看到 |
| 已清除 | 有擦除记录 | 没有人，不可逆 |

### 2.2 操作

| 操作 | 谁 | 条件 | 结果 |
|---|---|---|---|
| 直接删除 | 创建者 | 正常或待申请 | 新一轮，`purge_after = deleted_at + 168 小时`（数据库时钟）。待决定的编辑申请被拒绝，待决定的删除申请记为同意 |
| 请求删除 | 伴侣 | 没有任何待决定申请 | 一条申请，回忆不变。不带文字 |
| 同意 | 创建者 | 申请未决定 | 决定和新一轮在同一事务提交 |
| 拒绝 | 创建者 | 申请未决定 | 回忆不变，之后可再次申请 |
| 撤回 | 申请人 | 申请未决定 | 回忆不变，之后可再次申请 |
| 撤销 | 该轮的删除者（即创建者） | 严格早于截止时刻，且无擦除记录 | 回忆恢复。撤销指明确切的一轮 |
| 清除 | 任务 | 到期且未撤销 | 文本被覆盖，不可逆（第 5 节） |

- 编辑申请和删除申请合计每条回忆最多一条待决定，互相阻止。创建者的直接编辑在待申请时同样被拒绝。
- 撤销不恢复已被拒绝的编辑申请，也不改已同意的删除申请的历史。撤销后可以再次申请。
- 可以多轮：删除、撤销、再删除。旧轮次的撤销和重放不影响新轮次，规则与照片删除相同。
- 重放按调用者、操作和键分类，只返回该轮或该申请的事实，**不返回标题、描述或照片**。

### 2.3 确认文案（提议）

文案只说明应用内的行为。备份何时过期要等生产验证（第 9 节），所以不写任何时间承诺。

创建者删除，或同意删除申请时：

> 删除这条回忆？删除后你们两人都看不到它。7 天内你可以在“最近删除的回忆”里撤销，之后文字会被擦除，不能恢复。你上传的照片会一起删除。对方上传的照片不会删除，仍由对方决定。关联计划里的标题、地点和备注会保留，不会被删除。已经打开过的内容、之前发出的链接和已保存的副本无法收回。

伴侣申请删除时：

> 申请删除这条回忆？创建者同意后，你们两人都看不到它。你上传的照片不会被删除，之后仍可在“保留的照片”里查看或删除。关联计划里的标题、地点和备注会保留。

### 2.4 申请的存储（需决定）

4.8 说“通过现有申请流程”，`phase3-plan.md` 第 7 节的草图有 `kind (edit, delete)`，但**实际的 `memory_edit_proposals` 没有 `kind`**，并且 `memory_date`、`text_id` 必填，延迟触发器要求 1 到 9 张照片。删除申请无法放进去，除非放宽这些约束。提议新建 `memory_delete_requests` 和 `memory_delete_decisions`，行为（一条待决定、同意/拒绝/撤回、重放）与现有流程一致。

## 3. 伴侣上传的照片（需决定）

回忆可以含伴侣的照片：伴侣提交申请、创建者同意后，绑定记为 `bound_by = 创建者`，`uploader_id` 仍是伴侣。

| | **A：隐藏回忆，保留照片（推荐）** | B：连同照片字节一起删除 |
|---|---|---|
| 是否符合 D6a | 符合：照片由上传者决定 | **与 D6a 冲突**：创建者销毁了别人的照片 |
| 上传者访问 | 不变：事实和原图都可读，任何时候都能自己删除 | 提交后立即失去，上传者本人也读不到 |
| 创建者访问 | 提交后失去（404）。**需要改 `usapp_media_shared_now`**，否则绑定到回忆的照片永远可读 | 提交后失去 |
| 原绑定 | 保留，永不改绑。照片不能再加入其他回忆或相册 | 保留，作为证据 |
| 撤销后 | 照片回到回忆，双方恢复访问。若上传者期间已删除，显示占位符 | 只有创建者能撤销，上传者无法自行恢复。`0035` 的守卫和“只有原删除者可撤销”也要放宽 |
| 清除后 | 回忆文字消失。字节留到上传者自己删除，继续计入空间配额 | 字节被清除，不可恢复 |
| 主要风险 | 上传者需要入口才能找到这些照片（见下）。字节可能长期保留 | 一方可以永久销毁另一方不可替代的照片 |

选 A 带来的新要求：**这些照片没有入口。** 回忆没了，照片又不能加入相册，上传者只能靠 ID 访问。提议增加一个只给上传者的只读列表，列出“所属回忆已删除、自己未删除”的照片，界面可显示缩略图并提供 D6 删除。

**创建者自己的照片（需决定，推荐级联）：** 删除回忆时，为创建者上传且尚未删除的每张绑定照片建立一轮 `media_deletions`，时间与回忆这一轮相同，并记录关联。撤销回忆时一并撤销这些轮次，事先单独删除的轮次不受影响。到期后由现有媒体清理任务清除字节。这些关联轮次不进入照片恢复列表，也不能单独撤销，否则回忆还在已删除状态时照片就会复活。替代方案是不级联，让创建者逐张删除，改动更小，但删除回忆后字节仍然保留。

## 4. 读写路径

“已删除”指窗口内，“撤销”指撤销后，“已清除”指擦除后。伴侣和创建者分开写的地方都已注明。

### 4.1 回忆

| 路径 | 当前实现 | 已删除 | 撤销 | 已清除 |
|---|---|---|---|---|
| 时间线 `listMemories` | `USAPP_LIST_SQL` 不过滤 | 不列出，分页不受影响 | 回到原位置 | 不列出 |
| 详情 `getMemory` | 按空间读取 | `MEMORY_NOT_FOUND` | 恢复 | `MEMORY_NOT_FOUND` |
| 申请详情 `getProposal` | 含原文和建议全文 | `MEMORY_NOT_FOUND`（历史文字不外露） | 恢复 | `MEMORY_NOT_FOUND` |
| 编辑、提交申请、决定 | `kTargetSql` 只看成员和回忆存在 | `MEMORY_NOT_FOUND`，先查再分类 | 恢复 | 同已删除 |
| **创建的同键重放** | `createStart` 不走 `kTargetSql`，`classify` 经 `kCurrentInTxSql` **返回回忆全文** | **必须改**：返回 `MEMORY_NOT_FOUND`，否则重放旧键可读出已删除内容 | 恢复 | 同已删除。重放绝不能返回擦除后的占位文字 |
| 历史修订和照片 | 只追加 | 保留，无读取途径 | 恢复 | 保留，文字已覆盖 |
| 待决定的编辑申请 | 预留未绑定照片 | 提交时拒绝（`decided_by = 创建者`），预留释放，`unattached` 计时重启 | 保持已拒绝 | 文字被覆盖 |
| 数据库守卫 | 修订、申请、决定、绑定 | 全部增加拒绝，防止直接 SQL 绕过服务 | 恢复 | 永久拒绝 |

`usapp_memory_link_check` 等延迟检查不受影响，因为没有新修订。

### 4.2 照片

| 路径 | 当前实现 | 已删除 | 撤销 | 已清除 |
|---|---|---|---|---|
| 伴侣读取回忆里的照片 | `usapp_media_shared_now` 只要绑定到回忆就为真，**永远可读** | **必须改**：所属回忆已删除时为假，新请求 404，不签名 | 恢复（照片本身未删除时） | 404 |
| 上传者读取自己的照片 | `visibleTo` 上传者恒真 | 未删除的照片继续可读，这是方案 A 的本意 | 不变 | 不变 |
| 级联照片（创建者的） | `media_deletions` | 所有人 404 | 随回忆恢复 | 按现有规则清除字节 |
| 已签发链接 | 无法收回 | 伴侣手里的链接最多再用 10 分钟，或到对象被清除 | — | 保留照片的旧链接过期后失效 |
| 已下载副本和浏览器缓存 | 无法召回 | 无法召回 | — | 无法召回 |
| 加入其他回忆或相册 | 绑定主键：一张照片一个绑定 | 仍被拒绝 | 不变 | 仍被拒绝，不改绑 |
| `unattached` 清理 | 已绑定不参与 | 不参与 | 不变 | 不参与，保留的字节不会被自动清除 |
| 清理任务和迟到对象 | 不看回忆 | 不变 | 不变 | 不变 |

### 4.3 恢复列表和计划

| 路径 | 当前实现 | 已删除 | 撤销 | 已清除 |
|---|---|---|---|---|
| 照片恢复列表 `GET /media/deletions` | `USAPP_UNDOABLE_SQL` 读取回忆标题 | **必须改**：回忆已删除时 `kind = unavailable`，无 ID、无标题。否则会把标题显示给伴侣，清除后还会显示占位文字。关联轮次不列出 | 恢复上下文 | `unavailable` |
| 回忆恢复列表（新） | 无 | 只给创建者：轮次、回忆 ID、当前标题、时间。伴侣看不到 | 消失 | 消失 |
| 保留照片列表（新，方案 A） | 无 | 只给上传者 | 消失 | 继续列出 |
| 计划详情 | `SharedPlanController::detail` 返回 `memory_id` | **提议**：`memory_id` 为空，并增加 `memory_unavailable: true`。不返回标题，本来也没有 | 恢复 | 同已删除 |
| 计划列表 | `kListSql` 不含 `memory_id` | 不变 | 不变 | 不变 |
| 关联已有回忆 `usapp_plan_memory_attach` | 只查回忆存在 | **必须改**：已删除或已清除时返回 `not_found`。守卫 `usapp_plan_memory_link_guard` 同样拒绝 | 恢复 | 拒绝 |
| 已有关联 `shared_plan_memory_links` | 不可变，每计划一条，有外键 | 保留，只存 ID | 恢复显示 | 保留。**计划不能再关联其他回忆**（需决定） |
| 从计划创建回忆的重放 | 经过上面的创建重放 | 返回 `MEMORY_NOT_FOUND`，不是 `missing_receipt` 错误 | 恢复 | 同已删除 |
| 计划自己的文字 | `shared_plan_events.request` 和 `body`，对两名成员可读 | **不受影响，继续显示（O12）** | 不变 | **不擦除** |

### 4.4 其他

- 通知和推送：没有任何路径写入回忆文字（`Notification*`、`Push*`、`Reminder*` 只有 C++ 头文件的 `<memory>`）。首页没有回忆。之后若加回忆通知，必须重新审查。
- 审计：`memory.*` 的 `detail` 只有 ID、版本、结果和数量。新增动作同样不带文字。
- 前端：Pinia 只在内存里，身份切换时清空。对方页面在下次读取前仍显示旧内容，文案应说明。`/api/` 不进服务工作线程缓存。

## 5. 文本擦除

### 5.1 4.8 的假设与实际不符

4.8 写的是“一张有删除途径的表，经由 `SECURITY DEFINER` 函数”。实际上：

- `memory_revisions.text_id` 和 `memory_edit_proposals.text_id` 都是 `NOT NULL`，并有 `FOREIGN KEY (text_id, couple_id) ... ON DELETE RESTRICT`。
- 这两张表只追加，语句级触发器拒绝一切 `UPDATE`。
- 所以**删除 `memory_texts` 的行必须先修改不可变的修订和申请行**，或者放弃外键。
- 仓库目前没有任何 `SECURITY DEFINER` 函数（`0019` 明确不用），这会是第一个。

| 方案 | 外键和不可变行 | 结果 |
|---|---|---|
| **覆盖文字（推荐）** | 都不动：行还在，`text_id` 不变 | `title` 变为固定占位，`description` 变为空。满足现有 CHECK |
| 删除文字行 | 要把 `text_id` 改成可空、放宽 CHECK，并更新每条修订和申请 | 改动最大，还破坏“不可变” |
| 加密后销毁密钥 | 需要密钥管理和迁移旧数据 | 超出本批，留给 D5 |

### 5.2 保留的文字副本

| 位置 | 内容 | 清除时 |
|---|---|---|
| `memory_texts.title`、`description` | 当前版本、所有旧版本、所有申请（含已拒绝和已撤回）的文字。**没有 `memory_id` 列**，靠修订和申请反查 | 覆盖 |
| `memory_revisions.request_fingerprint` | 对日期、标题、描述和照片 ID 的**无盐 SHA-256**。短标题可用字典反推 | 提议覆盖为固定值（需决定） |
| `memory_edit_proposals.request_fingerprint` | 同上 | 同上 |
| `memory_edit_decisions.request_fingerprint` | 只含 ID 和结果 | 保留 |
| `memory_date`（修订、申请） | 日期，不在 4.8 的擦除范围 | 提议保留（需决定） |
| `audit_logs` | `memory.*` 只有 ID、版本、结果和数量；`shared_plan.*` 只有 `event_id` | 保留 |
| `shared_plan_memory_links` | 只有 ID 和请求键 | 保留 |
| **`shared_plan_events.request`、`body`（不是回忆的副本）** | 计划的标题、日期、时间、地点和备注。每次创建、编辑和申请都写两份，全部版本永久保留。计划目前没有删除途径（4.8 留给计划自己决定） | **不擦除（O12）。** 这是计划自己的文字，不是回忆的副本：从计划创建回忆时表单是空的，文字由用户另外填写（`SharedPlanDetailView.vue`），代码不会复制。但用户可能写了相同的内容，所以确认文案必须说明 |
| PostgreSQL 死元组、WAL、副本、备份 | 覆盖前的旧版本 | **数据库内做不到**：要等 vacuum 和备份到期，属于生产门槛 |
| 服务器和 PostgreSQL 日志 | 代码没有记录文字；默认配置不记录参数值 | 验收时用哨兵文字检查隔离实例的日志，生产配置列入门槛 |
| 对方的屏幕、截图 | | 无法召回 |

### 5.3 机制

- 不可变性只放开一条窄路。`memory_texts` 的语句级触发器换成：`DELETE`、`TRUNCATE` 仍拒绝；`UPDATE` 由行级守卫检查，只允许变成固定占位，且该文字所属回忆已有擦除记录。两张表的指纹用同样方式，只允许这一列变成固定值。
- `usapp_api` 仍然没有 `UPDATE` 权限。只有所有者身份的 `usapp_memory_erase(p_deletion uuid)` 能写，`search_path` 固定，`REVOKE ... FROM PUBLIC`，只授权给 `usapp_api` 执行。函数自己重新检查：确切的一轮、未撤销、数据库时钟已到期。权限检查清单同步更新。
- 文字可能被共用：同意申请时修订直接使用申请的 `text_id`。`memory_texts` 没有约束阻止不同回忆共用，服务不会这样做，但函数必须检查。若发现文字还被另一条未清除的回忆引用，**拒绝并报错，不覆盖**。
- 清除在一个事务内完成：33020，排序后的 33018，写 `memory_purges`，覆盖文字和指纹。整个过程不访问对象存储，所以不需要重试状态。任务 `memory.purge` 独立于 `media.cleanup`，后者继续只持有 33018。
- 字节的清除仍由 `media.cleanup` 负责。文字和字节不要求同时完成：两者的截止时刻相同，读取在提交时已经停止。
- 所有读取在到达文字前先看已删除状态，所以占位文字不会出现在任何响应里。验收时断言这一点。

## 6. 最小实现批次

**批次 M1：仅后端，模拟对象存储，一次性实例。** 前端另算 M2。不做相册和计划的删除、真实对象存储、外部日志和备份。

### 6.1 共同约定

- 迁移从 `0036` 开始，每步一个增量迁移，`0000`–`0035` 不动。每个迁移在首次提交后冻结，所以每步都要先做两种角色的回滚预检。
- 锁序沿用现有：成员 → 33020 → 分类 → 排序后的 33018。不需要新锁类。任务只按 33020 → 33018 取锁，绝不反向。
- **SQLSTATE 用 `UE` 族。** `UM` 已被 `0015`、`0016` 占用，不能用。已检索工作区的迁移、测试、服务、契约、脚本和文档：已占用 `UB UC UD UF UG UH UK UL UM UN UP UQ UR UT UV UW UX UY UZ`；`UE` 没有任何匹配（`UA UI UJ UO US UU` 同样空闲）。分配：`UE001` 只追加，`UE002` 删除，`UE003` 撤销，`UE004` 申请，`UE005` 决定，`UE006` 擦除。
- 错误码：`MEMORY_ALREADY_DELETED`、`MEMORY_UNDO_CLOSED`、`MEMORY_DELETION_NOT_ACTIVE`。申请复用 `MEMORY_PROPOSAL_PENDING`、`MEMORY_PROPOSAL_DECIDED`、`MEMORY_PROPOSAL_NOT_FOUND`。
- 所有步骤完成并通过发布门槛之前都不部署。每步的回滚风险是为之后的发布准备的。

### 6.3 回滚和恢复风险

“旧构建”指回退到这一步之前的代码，数据库不回退。迁移都是只增不减的，不提供降级脚本。

|---|---|---|---|
| M1a | 旧构建不看轮次：**已删除的回忆重新显示**，伴侣又能读照片。编辑被守卫拒绝，表现为 500 | 轮次丢失，回忆重新出现。需要外部日志防止 | 可挽回：文字和字节都还在。但隐私承诺失效，所以任何回忆删除发生后都不应回退到 M1a 之前 |

### 10.5 过程中的失败，如实记录

- 第一次构建：测试辅助函数只接受两个参数，修正测试。
- 第一次运行：**D6c 基线镜像**的 `db_gated` 崩溃，发生在任何 0036 工作之前，详见下一段。
- 验证脚本：账本文件的 CRLF 行尾和账本顺序各失败一次（计划关联账本留下的孤立回忆不能排在检查延迟约束的账本之前），修脚本。
- 新账本：批准修订的键必须为空，修夹具。

### 14.2 权限边界

这是仓库第一个 `SECURITY DEFINER` 函数。**函数所有者不是超级用户，这是对 5.3 的收窄：** 5.3 写的是“所有者身份”，而迁移由超级用户执行，如果沿用，函数就会以超级用户身份运行。

| 主体 | 能做什么 | 不能做什么 |
|---|---|---|
| `usapp_memory_eraser`（函数所有者） | `NOLOGIN`，不是超级用户，没有成员，也不属于其他角色。只能 `UPDATE` 四列：`memory_texts.title`、`description`，两张表的 `request_fingerprint`。可以 `INSERT memory_purges`，读 6 张需要的表 | 其他任何写入。读不到计划事件，碰不到审计 |
| `usapp_api` | 执行函数，读 `memory_purges` | 这些列的任何 `UPDATE`，写 `memory_purges`，取得 eraser 角色 |
| `PUBLIC`、`usapp_push` | 无 | 不能执行函数 |
| 超级用户直接执行 SQL | 触发器仍然生效：`UPDATE` 答 `USAPP_MEMORY_APPEND_ONLY`，`INSERT memory_purges` 要过守卫 | 超级用户可以关闭触发器，这一点不可防 |

- **函数：** `SET search_path = pg_catalog, pg_temp`，所有对象都写明 `public.`。`PUBLIC` 的执行权已撤销。它自己重新检查：确切的一轮存在、未撤销、数据库时钟已到期，文字没有被未擦除的回忆共用。
- **窄路：** `DELETE` 和 `TRUNCATE` 一律拒绝。`UPDATE` 对 eraser 以外的人和以前一样拒绝，哪怕一行都不影响。即使是 eraser，也只能写这些固定值，只能写有 `memory_purges` 记录的回忆。而这条记录本身要过守卫：确切的一轮、未撤销、已到期。
- **先验证：** `memory_erase_privilege_test.sql` 在回滚预检和提交后都最先运行，在任何服务用例之前，两个角色各一次。C++ 的第一个用例再用真实登录验证 `usapp_api` 得到 `permission denied`，包括 `SET ROLE`，并验证超级用户被触发器拒绝。

### 14.4 与设计的出入

1. **函数所有者是专用角色，不是迁移身份。** 见 14.2，权限比设计更窄。
2. **只取 33020，不取 33018。** 5.3 写了排序后的 33018，但擦除不写任何照片行。
3. **不写审计行。** eraser 碰不到 `audit_logs`，`memory_purges` 就是记录，任务结果只有数量。如果需要审计行，要扩大这个角色的权限，这由评审决定。

- 校验看的是当前数据库。这个角色在同一集群其他数据库里的表和授权，只能在那个数据库上运行时才查到。

### 15.2 为什么用 `memory_purges` 做擦除记录

这是实现时的选择，14.4 第 3 条把它留给评审决定，**所有者尚未批准**。理由如下：

- **不写 `audit_logs`。** eraser 角色碰不到审计表。写审计就要扩大这个不可逆函数所有者的权限，而它的安全性正来自权限窄。
- **它本身就是不可变记录。** 只追加，一条记录对应确切的一轮（外键），每条回忆最多一条，只有函数能写，自带守卫：确切的一轮、未撤销、已到期。
- **它是窄路的前提。** 文字和指纹的守卫都要求有这条记录，所以记录和覆盖在同一事务里，不可能只有其一。
- **它不含文字。** 只有 ID 和时间。`usapp_api` 可读。
- **代价：** `audit_logs` 里查不到擦除。查询必须看 `memory_purges`。如果以后需要统一的审计视图，应由另一个有审计权限的步骤读取这张表，而不是扩大 eraser。

**更正（2026-11-05，调查后）：** 这次运行还有第二个失败，上面和当时的报告都漏掉了：`db_gated` 的 “P2-2: proposals...”，3 个断言，同样由 `USAPP_NOTIFICATION_SOURCE` 引起，时间正好早 30.001 秒。后续调查和证据见 `docs/phase3-timestamp-guards.md`，它取代本节关于时钟的结论。

**证据能确定的条件：** 这条语句是 `INSERT INTO notifications ... SELECT ... FROM usapp_notification_optional_source`，所以身份列直接来自守卫比较的同一行，不可能不同。来源行存在，否则这条语句插入不了任何行。**排除之后只剩守卫的两个时间比较之一：** `NEW.created_at < facts.occurred_at` 或 `NEW.created_at > clock_timestamp()`。证据无法分辨是哪一个。这是由代码推断的，不是观察到的。

**更正第 13 和 14 节的说法：** 之前的时钟探针“回退 0 次”几乎说明不了问题。它每次采样之间要睡 1 毫秒以上，而这些守卫比较的是相隔几微秒的两次读取，亚毫秒的回退它看不见。

**新探针（`usapp-clock-20261105203253-d6ca27`，`Claude outputs/clock-tight-probe.ps1`）：** 在只有 PostgreSQL、没有应用的一次性集群里，连续读取 `clock_timestamp()`，中间没有任何操作。容器内可见 32 个 CPU。

| 轮次 | 会话数 | 样本数 | 回退次数 | 最大回退 |
|---|---|---|---|---|
| 单会话 | 1 | 50,000,000 | 1 | 1567 微秒 |
| 所有 CPU | 32 | 310,105,312 | 32 | 1601 微秒 |
| 两倍 CPU | 64 | 324,589,524 | 33 | 1577 微秒 |

**结论：这个 Docker 环境里，数据库时钟确实会回退大约 1.6 毫秒，没有任何应用在运行也会。** 第二轮的 32 次看起来是一次回退被 32 个会话都看到了，这是推断。

**这说明什么：** 任何守卫，只要比较相隔不到约 1.6 毫秒的两次时钟读取，碰巧跨过一次回退就会拒绝正常的写入。P2-3b（`USAPP_NOTIFICATION_INTENT_SOURCE`）、M9（`USAPP_REDEMPTION_EVENT_TIME`）和这次的 P2-5b（`USAPP_NOTIFICATION_SOURCE`）都是这种形状。

- **原因没有被证明。** 还没有在一次失败发生的同一时刻捕捉到一次回退。
- P3-1a 和 `DbClient` 崩溃不是这种形状，这个解释不覆盖它们，仍未解决。
